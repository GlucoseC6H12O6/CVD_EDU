# 08-07 · Data-driven Process Engineering

현대의 CVD 장비는 매 초 수십 가지의 Sensor 값을 기록하고, 계측 장비는 Wafer마다 두께와 결함 데이터를 남긴다. 이 데이터를 잘 활용하면 공정의 변화를 빨리 알아채고, 계측하지 않은 Wafer의 결과를 예측할 수도 있다. 그러나 데이터를 잘못 다루면 그럴듯하지만 틀린 결론에 이르기 쉽다. 이 장에서는 공정 데이터의 구조와 연결, 전처리와 품질 점검, 분석의 재현성, 예측 모델의 개발과 배포, 그리고 실무에서 모델을 평가하고 운영하는 방법을 배운다.

> 근거 표시 — **[논문]** 논문에 보고된 값 · **[특허]** 특허의 주장·실시예 · **[리뷰]** 교과서 수준의 정설 · **[계산]** 가정을 밝힌 교육용 계산 · **[현장]** 문헌으로 못 박지 못한 현장 통념(자기 장비에서 확인해야 한다). 번호는 장 끝 참고 목록의 번호이다.

## 1. 데이터 원천과 구조

### Sensor Trace·Recipe Step·계측·PM 이벤트

공정 데이터는 여러 원천에서 나온다. Sensor Trace는 공정 중에 장비가 기록하는 압력, 온도, RF 전력, 유량 같은 시계열 데이터이다. Recipe와 Step 정보는 언제 어떤 조건으로 공정했는지를 알려 준다. 계측 데이터는 공정 뒤에 측정한 두께, 굴절률, 결함 수 등이다. PM 이벤트는 장비를 정비하거나 부품을 바꾼 기록이다 [현장].

이 데이터들은 서로 다른 키와 시간 단위를 가진다. Sensor Trace는 초 단위로 기록되지만, 계측 데이터는 Wafer 단위로, PM 이벤트는 날짜 단위로 기록된다. 그래서 이들을 연결하려면 먼저 구조를 이해해야 한다.

장비 센서 데이터가 어떤 모양의 자료 구조가 되는지 보자 [논문 1].

Wafer i(1–N)마다 센서 변수(SVID) j(1–M)를 시간 k(1–nᵢ)에 따라 기록한다. 위의 노란 표는 한 센서 변수를 Wafer별로 늘어놓은 것이고, 아래 파란 표는 Wafer 하나의 모든 센서를 시간에 따라 늘어놓은 것이다. 각 Wafer에는 정상/이상 표시(Label)가 붙는다. ### Wafer·Lot·Chamber 연결 키

서로 다른 데이터를 합치려면 공통된 키가 필요하다. 보통 Wafer ID, Lot ID, Chamber ID, Step 번호, 그리고 시간이 연결 키로 쓰인다. 예컨대 어떤 Wafer의 두께와 그 Wafer를 처리할 때의 Sensor Trace를 연결하려면, Wafer ID와 Chamber ID, 그리고 처리 시간이 일치해야 한다.

데이터를 합치기 전에 각 키의 의미를 분명히 정의해야 한다. 같은 이름의 "Chamber"가 한 시스템에서는 장비의 Chamber를, 다른 시스템에서는 Load Lock을 뜻할 수도 있다.

### 시간대·Timestamp·Sampling 주기

시간을 기준으로 데이터를 연결할 때는 특히 주의해야 한다. 장비마다 시계가 조금씩 다를 수 있고, 시간대(Timezone) 설정이 다를 수도 있다. 또 Sensor마다 기록하는 주기(Sampling Rate)가 다르다. 압력은 0.1초마다, 온도는 1초마다 기록된다면 두 데이터를 맞추는 방법을 정해야 한다. 시간이 몇 초만 어긋나도 Step 전환의 과도 상태를 정상 상태로 잘못 볼 수 있다 [현장].

> 이해 확인: 계측 시스템의 시간이 장비 시간보다 1시간 앞서 있다면 Wafer 두께와 Trace를 시간으로 연결할 때 어떤 일이 생기는가?

## 2. 전처리와 데이터 품질

### 결측·이상값·단위·중복의 확인

분석하기 전에 데이터의 품질을 점검해야 한다. 값이 빠진 결측, Sensor가 측정 범위를 넘어 최댓값에 고정된 포화, 장비 시계가 조금씩 어긋나는 Clock Drift, 같은 기록이 두 번 들어간 중복, 그리고 서로 다른 단위가 섞인 경우(예: Torr와 mTorr) 등을 확인한다. 이런 문제가 있는 데이터로 분석하면 결과가 왜곡된다 [현장].

### 정렬·집계·특징 추출

품질을 점검한 뒤에는 데이터를 분석할 수 있는 형태로 만든다. 시간이 다른 데이터를 같은 시간 축에 맞추는 것을 정렬이라고 한다. Trace 같은 긴 시계열을 Step별 평균, 최댓값, 기울기 같은 몇 개의 값으로 요약하는 것을 집계라고 한다. 그리고 공정 지식을 바탕으로 의미 있는 값을 만들어 내는 것을 특징 추출(Feature Engineering)이라고 한다. 예컨대 Plasma 점화 뒤 반사 전력이 안정되는 데 걸린 시간은 Matching 상태를 나타내는 좋은 특징이 될 수 있다.

### 실측값과 보간값의 구분

결측값을 채울 때는 주의해야 한다. 결측값을 단순히 평균으로 채우면, 실제로는 장비 고장 때문에 값이 빠진 패턴을 지워 버릴 수 있다. 또 사이 값을 추정해 채운 보간값은 실제로 측정한 값이 아니다. 그래서 어느 값이 실측값이고 어느 값이 보간값인지 표시해 두어야 한다. 그래야 나중에 결과를 해석할 때 보간값이 결론을 좌우하지 않았는지 확인할 수 있다 [리뷰 2].

> 이해 확인: 어떤 Sensor의 값이 특정 Chamber에서만 자주 빠져 있다. 이 결측값을 평균으로 채우면 어떤 정보를 잃는가?

## 3. 분석의 재현성

### Notebook·Script·환경·Random Seed

데이터 분석은 다른 사람이, 또는 나중의 자신이 같은 결과를 다시 얻을 수 있어야 한다. 이를 재현성이라고 한다. Python 분석 코드는 입력 데이터의 구조(Schema), 단위, 실행 환경, Library의 Version, 그리고 무작위 과정의 Seed를 기록해 재현할 수 있도록 작성한다. Notebook은 탐색에 편리하지만 실행 순서에 따라 결과가 달라질 수 있으므로, 최종 분석은 처음부터 끝까지 한 번에 실행되는 Script로 정리하는 것이 좋다.

### 데이터·설정·결과의 Version 관리

분석에 쓴 데이터, 분석 설정, 그리고 결과를 함께 Version으로 관리한다. 데이터가 나중에 갱신되면 같은 코드로도 다른 결과가 나올 수 있으므로, 어떤 Version의 데이터로 분석했는지 기록해야 한다. 분석 자료와 결과 보고서를 따로 보관하면 현장의 대용량 데이터를 다루기에도 편리하다.

### Unit Test와 Schema 검증

분석 코드가 의도대로 동작하는지 확인하기 위해 Unit Test를 작성한다. 예컨대 단위 변환 함수가 Torr를 Pa로 정확히 바꾸는지 시험한다. 또 입력 데이터가 예상한 구조와 범위를 가지는지 Schema 검증으로 확인한다. 데이터의 형식이 바뀌었는데 코드가 이를 알아채지 못하면, 오류 없이 틀린 결과를 낼 수 있다.

> 이해 확인: 같은 Notebook을 다시 실행했더니 결과가 조금 달랐다. 무엇을 확인해야 하는가?

## 4. 모델 개발

### 기준 모델과 시간·Chamber 단위의 분할

예측 모델을 만들 때는 먼저 단순한 기준 모델(Baseline)을 정한다. 예컨대 "이전 Wafer의 두께로 다음 Wafer의 두께를 예측한다" 같은 단순한 방법이다. 복잡한 모델은 이 기준 모델보다 의미 있게 좋을 때만 쓸 가치가 있다 [리뷰 2].

모델을 평가할 때는 데이터를 시간이나 Chamber 단위로 나눈다. 과거 데이터로 학습하고 미래 데이터로 시험하면(Time-based Holdout), 모델이 실제로 앞으로의 Wafer를 잘 예측하는지 알 수 있다. 일부 Chamber로 학습하고 다른 Chamber로 시험하면(Chamber-based Holdout), 새로운 Chamber에도 모델을 쓸 수 있는지 알 수 있다 [리뷰 2].

### 회귀·분류·이상 탐지

공정 데이터로 만드는 모델은 목적에 따라 나뉜다. 회귀 모델은 두께처럼 연속된 값을 예측한다. 계측하지 않은 Wafer의 두께를 예측하는 가상 계측(Virtual Metrology)이 대표적이다. 분류 모델은 Wafer가 정상인지 불량인지 같은 범주를 예측한다. 이상 탐지 모델은 정상 데이터의 패턴을 배워, 그와 다른 패턴을 찾아낸다. 불량 데이터가 드물 때 유용하다 [리뷰 3].

### 누출·불균형·Drift의 고려

[Statistical & Causal Modeling](#ref:08-05)에서 본 것처럼, 같은 Wafer나 같은 Lot의 데이터가 학습과 시험에 모두 들어가면 데이터 누출이 생긴다. 또 불량 데이터가 정상 데이터보다 훨씬 적은 불균형이 있으면, 모든 Wafer를 정상으로 예측하는 모델도 정확도가 높게 나온다. 그리고 장비가 노화되면 데이터의 분포가 시간에 따라 변하는데(Drift), 과거 데이터로 만든 모델은 이런 변화에 따라 성능이 떨어진다 [리뷰 2].

> 이해 확인: 불량률이 1 %인 데이터에서 모든 Wafer를 정상으로 예측하는 모델의 정확도는 얼마인가? 이 정확도는 의미가 있는가?

## 5. 모델 배포

### 일괄 예측·Dashboard·경보·사람의 검토

모델을 만든 뒤에는 실제로 쓸 수 있도록 배포한다. 배포 방식에는 여러 가지가 있다. 하루에 한 번 모아서 예측하는 일괄 예측(Batch Scoring), 결과를 보여 주는 Dashboard, 이상이 있을 때 알려 주는 경보 등이다. 중요한 결정에는 모델의 결과를 그대로 쓰지 않고 엔지니어가 검토하는 단계를 둔다.

### Shadow Test·되돌리기·감사 기록

새 모델을 바로 실제 결정에 쓰기 전에, 일정 기간 실제 결정에는 영향을 주지 않으면서 예측만 기록해 보는 Shadow Test를 한다. 이 기간에 모델의 예측을 실측과 비교해 성능을 확인한다. 배포한 뒤에는 입력 데이터의 분포 변화와 모델의 오차를 추적하고, 문제가 생기면 이전 모델로 되돌릴 수 있도록 준비한다. 또 모델이 언제 어떤 예측을 했는지 감사 기록(Audit Log)으로 남긴다 [현장].

데이터 연결이 끊겼을 때 오래된 예측을 정상값처럼 화면에 보여 주어서는 안 된다. 데이터가 갱신되지 않았다는 것을 분명히 표시해야 한다.

### 장비의 실시간 제어와 분석 보고의 분리

[Advanced Process Control](#ref:07-07)처럼 모델의 결과로 장비의 Recipe를 실시간으로 바꾸는 것과, 분석 보고서를 만드는 것은 요구 수준이 다르다. 실시간 제어는 오류가 곧바로 공정에 영향을 주므로 훨씬 엄격한 검증과 안전장치가 필요하다. 그래서 분석용 모델을 검증 없이 실시간 제어에 연결해서는 안 된다.

> 이해 확인: 새 가상 계측 모델을 바로 APC에 연결하지 않고 Shadow Test부터 하는 이유는 무엇인가?

## 6. 실무 평가

### 정확도·정밀도·재현율·오경보·가치

모델은 공정에서 실제로 가치가 있는지로 평가해야 한다. 분류 모델이라면 정밀도(Precision, 불량으로 예측한 것 가운데 실제 불량의 비율)와 재현율(Recall, 실제 불량 가운데 찾아낸 비율)을 함께 본다. 오경보가 많으면 엔지니어가 경보를 무시하게 되고, 놓치는 불량이 많으면 모델을 쓰는 의미가 없다 [리뷰 2].

가상 계측은 실제 계측을 대신하는 것이 아니라, 어느 Wafer를 먼저 계측할지 정하거나 이상을 빨리 알아채는 보조 도구로 쓰는 것이 좋다.

### 현장의 제약·보안·설명 가능성

현장에서 모델을 쓰려면 기술 외의 조건도 고려해야 한다. 장비의 데이터 수집 주기나 계산 자원 같은 현장의 제약, 데이터의 보안, 그리고 엔지니어가 모델의 결과를 이해할 수 있는 설명 가능성이다. 보안 허가 없이 사내의 Trace나 Recipe를 외부 서비스로 보내서는 안 된다.

### 변경 관리와 운영 책임

모델도 장비의 Recipe처럼 변경 관리가 필요하다. 모델을 갱신할 때는 무엇이 바뀌었는지 기록하고 승인을 받는다. 또 모델이 틀린 결과를 냈을 때 누가 책임지고 대응하는지 운영 책임을 미리 정해 둔다.

> 이해 확인: 불량 예측 모델의 재현율은 높지만 정밀도가 10 %이다. 현장에서 이 모델을 쓸 때 생길 문제는 무엇인가?

이 식은 모델의 예측값과 실측값의 차이로 예측 오차를 나타낸다. 계산할 때는 예측값과 실측값의 단위가 같은지, 그리고 오차를 계산한 데이터가 모델 학습에 쓰이지 않은 독립된 데이터인지 확인해야 한다. 또 평균 오차만 보지 말고 오차가 시간이나 Chamber에 따라 어떻게 변하는지도 살펴야 Drift를 알아챌 수 있다.

**함께 알아 둘 관계식:** 정밀도·재현율·MAE·RMSE, 시간 단위 분할과 Drift 지표.

## 공정에서 확인할 데이터와 해석 순서 {h2:1}

데이터 기반 분석을 할 때는 먼저 데이터의 원천과 연결 키를 정의하고, 품질을 점검한다. 그다음 재현할 수 있는 코드로 특징을 추출하고, 시간이나 Chamber 단위로 데이터를 나누어 모델을 평가한다. 배포할 때는 Shadow Test와 되돌리기 계획을 세우고, 배포 뒤에는 Drift와 오차를 추적한다.

**실습 과제:** 가상의 장비 Trace CSV를 검증하고, 특징을 추출하고, 모델을 평가하는 절차를 작성해 보자.

## 오해와 적용 범위 {h2:2}

사내 인증 정보, 원본 Recipe, 고객 데이터를 외부로 보내지 못하도록 저장과 접근 정책을 분명히 정해야 한다. 데이터 기반 분석의 가치는 데이터를 안전하게 다룰 때에만 지킬 수 있다.

이 장의 기초 관계는 같은 장비에서 같은 Recipe를 쓰면 언제나 같은 물성과 결함이 나온다는 뜻이 아니다. 공정을 이해할 때는 직접 관찰한 사실, 문헌의 보고, 교육용 모델, 검증된 인과관계를 서로 구분해서 다루어야 한다.
